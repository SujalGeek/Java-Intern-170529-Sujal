### Summary of Factory Design Pattern Lecture

This lecture provides an in-depth explanation of the **Factory Design Pattern**, a fundamental concept in low-level design (LLD) and software engineering, widely used in real-world applications and interviews. The discussion emphasizes **separating object creation logic from business logic** to produce cleaner, more maintainable code by decoupling client code from the specifics of object instantiation.

---

### Core Concepts and Key Insights

- **Factory Design Pattern**: A creational design pattern where a separate class (factory) is responsible for creating objects. This decouples the client from knowing the details of object creation.
- **Motivation**: 
  - Avoid mixing business logic with object creation logic.
  - Simplify understanding and maintenance by separating concerns.
  - Enable flexible and dynamic object creation without exposing instantiation details to clients.
- **Relation to Strategy Pattern**:
  - Strategy pattern focuses on varying algorithms dynamically.
  - Factory pattern focuses on separating object creation from usage.
  - Both can sometimes solve similar problems but with different intents.

---

### Types of Factory Patterns Explained

| Factory Type          | Description                                                                                         | Pattern Status          |
|----------------------|-------------------------------------------------------------------------------------------------|------------------------|
| **Simple Factory**    | A class with a method that returns different objects based on input parameters (not a formal design pattern but a design principle). | Design Principle (Not a formal pattern) |
| **Factory Method**    | Defines an interface for creating an object but lets subclasses decide which class to instantiate. Supports multiple factory subclasses producing different objects. | Formal Design Pattern  |
| **Abstract Factory**  | Extends Factory Method to create families of related or dependent objects without specifying their concrete classes. Manages multiple product types. | Formal Design Pattern  |

---

### Example: Burger Shop Scenario

- **Product Hierarchy**:
  - Abstract class: `Burger` with an abstract method `prepare()`.
  - Concrete subclasses: `BasicBurger`, `StandardBurger`, `PremiumBurger`, each overriding `prepare()` with specific behavior.
- **Simple Factory**:
  - `BurgerFactory` class with a method `createBurger(type: string)` that returns an object of the requested burger type.
  - Uses conditional logic (if-else) to instantiate the correct burger based on the input type (`"basic"`, `"standard"`, `"premium"`).
  - Client code requests a burger by type without knowing instantiation details.
  
- **Factory Method**:
  - Abstract factory class `BurgerFactory` with an abstract method `createBurger(type)`.
  - Concrete factories (`SyncBurgerFactory`, `KingBurgerFactory`) override `createBurger()` to create different variants:
    - `SyncBurgerFactory`: creates normal burgers.
    - `KingBurgerFactory`: creates wheat-based burgers (`BasicWheatBurger`, `StandardWheatBurger`, `PremiumWheatBurger`).
  - The client decides which factory to use, and the factory dynamically creates appropriate burger types.
  
- **Abstract Factory**:
  - Factory responsible for creating families of related products, e.g., burgers and garlic bread.
  - Both `SyncBurgerFactory` and `KingBurgerFactory` implement methods `createBurger(type)` and `createGarlicBread(type)` to produce multiple related products.
  - Product families include normal and wheat-based variants of burgers and garlic bread.
  - This pattern allows creating sets of related products without the client knowing the concrete classes.

- Factory decides which notification object to create based on input type.
- Comparison with Strategy Pattern:
  - Strategy is used when the goal is to **change algorithms dynamically** during runtime.
  - Factory is used when the goal is to **abstract and centralize object creation**.
- Both patterns can be applied to similar problems depending on the design intent.
- Key takeaway: **Multiple design patterns can solve the same problem**, and the choice depends on the specific use case and intent.

### Summary: Builder Design Pattern Explained in Hindi

This video provides a detailed explanation of the **Builder Design Pattern** in software development, highlighting its advantages over the traditional Factory Design Pattern, particularly when dealing with complex object creation involving many parameters.

### Key Concepts and Problems with Factory Pattern

- **Factory Design Pattern** involves creating an object through a separate factory class or method that accepts all necessary parameters at once.
- When objects have **many parameters (e.g., 20, 30, 40+)**, passing all these parameters in the factory method or constructor becomes problematic.
- Issues include:
  - **Remembering the order** of parameters is difficult.
  - Handling **optional parameters** requires multiple overloaded constructors, increasing complexity.
  - The factory class holds **all responsibilities** for object creation, leading to potential code clutter and maintenance issues.

### Introduction to Builder Design Pattern

- The **Builder Pattern** solves these problems by allowing **step-by-step construction** of complex objects.
- It introduces a **Builder class** responsible for constructing the object incrementally by setting properties one by one.
- The object creation process is divided into multiple method calls, each setting a single property, which can be skipped if optional.
- Finally, a **build() method** returns the fully constructed object.
- This approach:
  - Eliminates the need to remember parameter order.
  - Simplifies management of optional parameters.
  - Delegates object creation responsibility to the builder class, keeping the main class clean.

### Implementation Details (as explained in the video)

- The main class (e.g., `User`) has a **private constructor** to prevent direct instantiation.
- The class contains **private fields** with **only getter methods** to maintain **immutability** — once created, the object’s state cannot be changed.
- A nested or separate **Builder class** contains the same fields and methods to set each property.
- Each setter method in the builder returns the builder itself (method chaining), allowing calls like:
  
  $$ \text{new User.Builder().setUserId(123).setUserName("Durgesh").build()} $$

- The `build()` method creates an instance of the main class with the accumulated properties.
- This pattern supports **optional parameters** easily by simply not calling the corresponding setter.
- The builder pattern improves **readability, maintainability, and usability** of code for complex objects.

### Benefits Highlighted

- **Immutability:** The created objects are immutable since setters are only in the builder.
- **Order Independence:** Properties can be set in any order without issues.
- **Simplified Object Creation:** Avoids constructor overloading and the confusion of multiple parameters.
- **Separation of Concerns:** Builder class handles construction; main class focuses on object representation.

### Example Use Case

- The video shows building a `User` object by setting `userId`, `userName`, and `emailId`, demonstrating:
  - Syntax of using the builder.
  - Skipping optional parameters.
  - Obtaining the final immutable user object.

### Summary of Prototype Design Pattern Video

The video provides a comprehensive explanation of the **Prototype Design Pattern**, focusing on its practical utility, implementation details, and real-world use cases, particularly in game development. The discussion is enriched with examples, UML diagrams, and code insights primarily in C++ (with references to Java). Below is a structured summary based strictly on the transcript content.

---

### Core Concept

- **Prototype Design Pattern** is a **creational design pattern** used to solve a very specific problem:  
  Creating new object instances by copying or cloning an existing object rather than creating a new one from scratch, which can be an **expensive operation**.
  
- This pattern is useful when object creation is costly due to operations like:  
  - Establishing database connections  
  - Performing complex calculations  
  - Loading files or resources  
  - Other time-consuming initialization tasks

- **Key Insight:** Instead of creating multiple expensive objects repeatedly, create one instance and then clone it to generate additional objects.

---

### Problem Statement

- Naively creating new objects involves calling constructors repeatedly, which could be expensive and time-consuming.  
- For example, creating multiple NPCs (Non-Player Characters) in a video game, where each NPC requires heavy initialization (e.g., loading images, database queries).  
- Creating 100+ NPCs this way would be inefficient.

---

### How Prototype Pattern Solves It

- Create one fully constructed object (prototype) once.  
- Use a **clone method** to create copies of this prototype, avoiding repeated expensive operations.  
- Cloning duplicates the object’s current state (values) without re-running the expensive initialization.

---

### Technical Implementation Details

1. **Classes and Methods:**

| Component             | Description                                                                                       |
|-----------------------|---------------------------------------------------------------------------------------------------|
| **Prototype (or Cloneable)** | An abstract class or interface with a pure virtual method `clone()` that returns a copy of the object. Acts as a *marker interface*. |
| **Concrete Prototype (e.g., NPC)** | Inherits from Prototype, implements `clone()` by using a **copy constructor** to duplicate itself. |
| **Copy Constructor** | Special constructor that takes a reference to an existing object and copies its values to create a clone. Avoids expensive re-initialization. |
| **Client**            | Uses the prototype reference to clone new objects instead of creating fresh instances.            |

2. **Copy Constructor Behavior:**

- Copies primitive data members (e.g., `int health`, `string name`, `int power`) directly from the original object.  
- This is a **shallow copy** when data members are primitives or immutable.  
- For non-primitive members (e.g., pointers or references to other objects), shallow copy means both clones point to the same underlying data, which might cause issues.

3. **Shallow Copy vs. Deep Copy:**

| Copy Type      | Description                                                                                 | Use Case / Notes                              |
|----------------|---------------------------------------------------------------------------------------------|-----------------------------------------------|
| **Shallow Copy** | Copies member values directly (e.g., pointers copied as addresses)                         | Efficient for primitives; problematic if objects contain pointers to mutable data. |
| **Deep Copy**    | Creates new copies of referenced objects in heap memory, duplicating entire data structure | Needed when clones must be independent; requires explicit allocation and copy of nested objects. |

- The video explains shallow vs. deep copy with examples of primitive and non-primitive data members in the prototype class.

---

### Example Use Case: NPC Characters in Games

- NPC creation simulates an expensive operation with database calls and complex calculations.  
- Prototype pattern allows:  
  - Create one NPC instance once (e.g., `npc1`), which performs all expensive initialization.  
  - Clone `npc1` to create `npc2`, `npc3`, etc., via `clone()` method, which internally uses the copy constructor.  
  - After cloning, minor differences (like health or power) can be adjusted using setters.  
- This approach **saves time and memory**, especially when many similar objects are required.

---

### UML Diagram Overview

| Role                   | Description                                                                                      |
|------------------------|-------------------------------------------------------------------------------------------------|
| **Client**             | Holds a reference to `Prototype` (or `Cloneable`) and requests cloning through `clone()` method.|
| **Prototype (Abstract)** | Declares `clone()` method to be implemented by concrete classes.                                |
| **Concrete Prototype** | Implements `clone()` by returning a new instance using the copy constructor.                    |

- The client interacts with the prototype reference polymorphically, enabling cloning without knowing the exact concrete class.

---

### Definitions and Key Points

- **Prototype Design Pattern Definition:**  
  *"Create new objects by copying or cloning an existing instance instead of calling a constructor repeatedly."*

- **Use Cases:**  
  - When object creation is expensive or time-consuming.  
  - When many similar objects with minor variations need to be created.  
  - Examples: NPCs in games, objects requiring heavy initialization like database connections or complex calculations.

- **Limitations:**  
  - Not suitable if objects differ significantly; cloning would require many setter calls, reducing efficiency.  
  - Deep copy implementation might be required for objects with complex internal structures.

---

### Summary Table: Comparison of Object Creation Approaches

| Approach                  | Pros                                       | Cons                                               |
|---------------------------|--------------------------------------------|----------------------------------------------------|
| **Direct Constructor Calls** | Simple, straightforward                   | Expensive if constructor does heavy lifting; slow when many objects needed |
| **Prototype Pattern (Clone)** | Efficient for creating many similar objects; reduces initialization overhead | Requires managing clone method and copy constructor; shallow copy may cause issues with referenced objects |

---

### Key Takeaways

- **Prototype Design Pattern optimizes object creation by cloning existing objects instead of reconstructing them from scratch.**  
- It leverages **copy constructors** to efficiently duplicate object state while avoiding expensive initialization tasks multiple times.  
- The pattern is ideal for scenarios like **game NPC creation**, where many similar but not identical objects are used.  
- Understanding **shallow vs. deep copy** is crucial for correct implementation, especially when objects contain references or pointers.  
- The pattern uses an **abstract prototype interface/class with a clone method** acting as a marker to indicate clonability.

---

### Summary: Adapter Design Pattern Explained

The video lecture provides a comprehensive explanation of the **Adapter Design Pattern**, emphasizing its practical utility, especially in software development and interview scenarios. The pattern is introduced with real-life analogies and a detailed programming example, along with UML diagrams and code walkthroughs.

---

### Key Concepts and Definitions

- **Adapter Design Pattern** enables incompatible interfaces to work together by converting the interface of one class into another that a client expects.
- It acts as a **bridge** between two incompatible interfaces, allowing classes or systems that normally cannot communicate to interact smoothly.
- The pattern is commonly used to integrate **third-party libraries** or **legacy code** with modern applications without tightly coupling the codebases.

---

### Real-Life Analogies

- Using an **international power adapter** to plug an Indian charger into a US socket.
- Employing a **Type-C to Type-A adapter** to connect cables of different types.

These examples illustrate how adapters enable devices (or code modules) with differing interfaces to work together.

---

### Problem Statement in Software Context

- Existing application code often needs to interact with third-party libraries or legacy systems.
- Third-party libraries may have completely different interfaces and return types than the existing code.
- Directly coupling application code to third-party libraries leads to tight coupling, making future changes or replacements difficult.
- Solution: Introduce an **adapter** between the existing code and third-party library to decouple them.

---

### Adapter Pattern Structure and Flow

| Component                 | Role                                                                                          |
|---------------------------|-----------------------------------------------------------------------------------------------|
| **Client (Existing Code)** | Expects a specific interface (e.g., `IReport` interface with `getJsonData()` method).         |
| **Adaptee (Third-party Library)** | Provides incompatible interface or data (e.g., `XmlDataProvider` with `getXmlData()` method). |
| **Adapter**                | Implements the client’s interface, holds a reference to the adaptee, converts adaptee’s data/interface to the client’s expected form. |

- The client interacts only with the adapter, unaware of the adaptee.
- Adapter calls the adaptee’s methods, converts the response (e.g., XML → JSON), and returns it to the client.

---

### Programming Example Overview

- **Interface:** `IReport` with a method `getJsonData(String rawData)`
- **Adaptee Class:** `XmlDataProvider` with method `getXmlData(String rawData)` returning XML formatted data.
- **Adapter Class:** `XmlDataProviderAdapter` inherits/implements `IReport`, holds a reference to `XmlDataProvider`.
- The adapter overrides `getJsonData()`, internally calls `getXmlData()` on the adaptee, converts XML to JSON, and returns JSON to client.
- The client calls `getJsonData()` on the adapter without knowing about XML or the third-party class.

---

### UML Diagram and Pattern Variants

| Pattern Type      | Description                                                                                       |
|-------------------|-------------------------------------------------------------------------------------------------|
| **Object Adapter** | Uses **composition**: adapter holds reference to adaptee and implements target interface.       |
| **Class Adapter**  | Uses **multiple inheritance**: adapter inherits both target and adaptee interfaces/classes.     |

- Object adapter is preferred due to flexibility and better adherence to composition over inheritance principle.
- Class adapter is less used because:
  - Multiple inheritance is not supported in many languages like Java.
  - Even if supported (e.g., C++), it is generally discouraged in real-world applications.

---

### Practical Use Cases

- **Third-Party Integration:** When integrating external services or libraries whose interfaces differ from your application.
- **Legacy Code Adaptation:** When modern applications need to interact with old legacy code without modifying it.
- **Interface Conversion:** When two systems or modules speak different “languages” or data formats (e.g., XML vs JSON).

---

### Standard Definition from the Video

> **Adapter converts the interface of a class into another interface the client expects.**  
> It allows classes to work together that couldn't otherwise because of incompatible interfaces.

---

### Summary Table of Components in the Example

|----------------------------|----------------------------------------------------------------------------------------------------|
| **Client**                 | Calls `getJsonData()` on `IReport` interface.                                                      |
| **IReport (Target Interface)** | Declares method `getJsonData(String rawData)`.                                                      |
| **XmlDataProvider (Adaptee)**| Provides method `getXmlData(String rawData)` returning XML formatted data.                         |
| **XmlDataProviderAdapter** | Implements `IReport`, holds reference to `XmlDataProvider`, converts XML data to JSON format.      |

---

### Important Insights

- The adapter **decouples** the client from the implementation details of the third-party library.
- It **enables reusability** of existing code without modification.
- The adapter pattern supports **interface compatibility** while preserving encapsulation.
- **Composition over inheritance** is the recommended approach for implementing adapters.
- This pattern is highly relevant for **code maintainability** when dealing with external dependencies or legacy systems.

### Summary: Bridge Design Pattern Explained

This video provides a detailed explanation of the **Bridge Design Pattern**, focusing on its problem-solving capability, structure, benefits, and real-world applications. The content is delivered through a practical example involving cars and engines, complemented by UML diagrams and code demonstrations.

---

### Problem Context: Class Explosion in Car-Engine Combinations

- Cars have multiple types (e.g., Sedan, SUV, Hatchback).
- Engines come in various types (e.g., Petrol, Diesel, Electric).
- Naively combining each car type with each engine type results in **$m \times n$ classes**, where:
  - $m$ = number of car types
  - $n$ = number of engine types
- For example, with 3 car types and 3 engine types, 9 classes are required.
- Adding a new engine type (e.g., CNG) exponentially increases the number of classes.
- This leads to **class explosion**, making the system complex and difficult to maintain.
- Violates design principles such as **SOLID** and **DRY** by forcing code duplication and tight coupling.

---

### Core Concept of Bridge Design Pattern

- **Bridge Pattern** proposes splitting a concept into two separate hierarchies:
  - **High-level part (Abstraction)**
  - **Low-level part (Implementation)**
- In the car-engine example:
  - High-level part = car types (Sedan, SUV, Hatchback) → *Abstraction*
  - Low-level part = engine types (Petrol, Diesel, Electric) → *Implementation*
- The **high-level abstraction holds a reference to the low-level implementation**, allowing both parts to vary independently.
- This reduces the number of classes from $m \times n$ to $m + n$.
- The pattern forms a **bridge** between the abstraction and the implementation, hence the name.

| Aspect               | Description                                         |
|----------------------|-----------------------------------------------------|
| High-level part      | Abstraction (e.g., car types)                        |
| Low-level part       | Implementation (e.g., engine types)                  |
| Relationship        | High-level holds a reference to low-level            |
| Result              | Independent variation of both hierarchies            |
| Class count reduction | From $m \times n$ to $m + n$ classes                 |

---

### How Bridge Pattern Works: Key Points

- Both abstraction and implementation are represented by **abstract classes**.
- Concrete subclasses implement the specifics:
  - Cars override the **drive()** method.
  - Engines override the **start()** method.
- The car abstraction delegates engine start responsibility to the engine implementation it holds.
- The abstraction does not depend on a specific implementation, promoting loose coupling.
- New car types or engine types can be added without modifying existing code, enhancing **extensibility**.

---

### Code and UML Structure Overview

- **Abstraction Layer:**
  - Abstract class `Car` with abstract method `drive()`.
  - Concrete classes: `SUV`, `Sedan`, `Hatchback`.
- **Implementation Layer:**
  - Abstract class `Engine` with abstract method `start()`.
  - Concrete classes: `PetrolEngine`, `DieselEngine`, `ElectricEngine`.
- The `Car` class holds a reference to an `Engine` object.
- `drive()` calls `engine.start()` internally.
- This design enables any car to be paired with any engine without creating combinations explicitly.

---

### Real-World Use Cases

- **Hardware example: TV and Remote Controls**
  - TVs (LCD, LED, OLED) represent implementations.
  - Remotes represent abstractions.
  - New TVs and new remotes can be developed independently and paired flexibly.
- **Software example: Graphical User Interfaces (GUI)**
  - GUI widgets (TextBox, Dropdown, RadioButton) are abstractions.
  - Operating Systems (Windows, Mac OS, Linux) are implementations.
  - GUI appearance varies by OS without changing widget logic.

---

### Comparison with Strategy Pattern

| Feature                  | Bridge Pattern                             | Strategy Pattern                          |
|--------------------------|-------------------------------------------|------------------------------------------|
| Intent                   | Decouple abstraction from implementation for independent variation | Define interchangeable algorithms for dynamic behavior changes |
| Structure                | Two separate hierarchies (high-level and low-level) with a reference bridge | One context with interchangeable strategies |
| Use Case                 | When both abstraction and implementation need independent extensibility | When algorithm behavior needs to be selected or changed dynamically by the client |
| Dynamic Behavior Change  | Not intended for runtime switching of implementation | Designed for runtime interchange of algorithms |
| Example                  | Car types and engine types combined flexibly | Car with dynamic engine strategy switching (less common) |

- Both patterns appear similar in UML but differ in **intent and use case**.
- Bridge focuses on **extensibility and reducing class explosion**, while Strategy focuses on **dynamic algorithm selection**.
- Bridge assumes a **fixed pairing** (e.g., a Sedan with Petrol engine remains so), not dynamic swapping at runtime.
- Strategy allows the client to change the strategy dynamically.

---

### Key Insights

- **Bridge Pattern prevents class explosion by separating abstraction and implementation.**
- It promotes **loose coupling** and **independent extensibility** of both parts.
- Useful when abstractions and implementations evolve independently.
- Enables **flexible pairing** of abstraction and implementation objects.
- Differentiated from Strategy by **intent**: Bridge for structural decoupling, Strategy for behavioral interchange.
- Real-world applicability spans hardware control systems and UI frameworks.
- Adheres to SOLID principles, especially **Open-Closed Principle** and **Dependency Inversion Principle**.

---

|----------------------------|----------------------|------------------------------------------|

| Bridge design pattern       | $m + n$ (e.g., 3 + 3 = 6) | Separate hierarchies for car and engine; combined at runtime via references |

### Conclusion

The Bridge Design Pattern is a **structural design pattern** that efficiently manages complexity arising from multiple dimensions of variation. By abstracting the high-level concept separately from its implementation, it allows software systems to scale gracefully, maintain cleaner codebases, and adhere to best design practices. Understanding when and how to apply Bridge, especially in comparison to similar patterns like Strategy, is crucial for designing flexible and maintainable software architectures.
